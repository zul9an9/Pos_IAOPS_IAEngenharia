# Tarefas

## 1. Estrutura do Projeto

- [x] 1.1 Criar o layout de pacote/módulo Python da CLI (ponto de entrada, `ssh_transport`, asset do script `collector`, parser de `baseline`, motor de `compliance`, escritores de `report`) e verificar que `python -m <entrypoint> --help` roda somente com a stdlib, sem `requirements.txt` nem imports de terceiros.
- [x] 1.2 Implementar o parsing de argumentos da CLI para endereço alvo, usuário, caminho da chave privada e caminho do arquivo de baseline, mais as flags opcionais `--aceitar-host-novo`, `--formato`, `--saida-json` e `--saida-markdown`, e verificar que argumentos incorretos ou ausentes saem com código `2` e uma mensagem de uso em linguagem simples (spec: baseline-compliance — Mensagem de Falha de Execução).

## 2. Transporte SSH (subprocesso do cliente do sistema)

- [x] 2.1 Implementar um wrapper de subprocesso que invoca o binário `ssh` do sistema com `-i <caminho-da-chave>`, `-o IdentitiesOnly=yes`, `-o BatchMode=yes`, `-o ConnectTimeout=<n>`, `-o StrictHostKeyChecking=yes`, alvo `user@host` e o comando remoto `sh -s` lendo de stdin, e verificar, inspecionando o argv montado em um teste unitário, que nenhuma biblioteca SSH é importada, que a chave é passada somente como caminho, que `IdentitiesOnly=yes` está presente (só a chave de `-i` é oferecida; design.md — D8), que `-v` nunca é passado e que o argv não contém `StrictHostKeyChecking=no` nem `UserKnownHostsFile` (spec: inventory-collection — Conexão SSH pelo Cliente do Sistema).
- [x] 2.2 Classificar os resultados do subprocesso em: sucesso, inalcançável/timeout, chave do host desconhecida ou alterada, autenticação rejeitada e outra falha — principalmente pelo status de saída do `ssh`, com o texto do stderr apenas como detalhe suplementar (a categoria "chave do host" usa o texto como apoio e, se não reconhecido, cai na falha geral de conexão) — e verificar com testes unitários que alimentam códigos de saída/fixtures de stderr sintéticos para cada categoria (design.md — D2, Risco sobre a fragilidade do stderr).
- [x] 2.3 Verificar que nenhum stdout/stderr/linha de log/mensagem de exceção capturado contém o **conteúdo** da chave privada, em todos os ramos de falha de 2.2, com um teste unitário que usa um arquivo de chave com conteúdo sentinela e afirma que essa string está ausente de todo texto capturado; verificar também que o caminho da chave só pode aparecer em mensagens de erro do stderr, e nunca em dado destinado a relatório (spec: inventory-collection — Confidencialidade da Chave Privada).
- [x] 2.4 Ligar os resultados de host inalcançável e autenticação rejeitada ao caminho de falha de execução da ferramenta (código de saída `2`) com uma mensagem em linguagem simples que nomeia o que ocorreu, e verificar por meio de um test double da chamada de subprocesso (spec: inventory-collection — Reporte de Falha de Conexão com o Host).
- [x] 2.5 Testar a política de `StrictHostKeyChecking` com um test double do subprocesso e, quando possível, com o `ssh` real contra o laboratório usando um `known_hosts` isolado: (a) por padrão, host desconhecido em `BatchMode` é recusado com código `2` e mensagem "chave do host desconhecida"; (b) com `--aceitar-host-novo` o argv passa a conter `StrictHostKeyChecking=accept-new` (e nunca `no`) e a conexão prossegue; (c) chave de host alterada continua recusada com código `2` mesmo com a flag (spec: inventory-collection — Verificação da Chave do Host; design.md — D2).

## 3. Script Remoto de Coleta

- [x] 3.1 Escrever o script de shell **POSIX** único (executado com `sh -s` e entregue por stdin em uma única sessão SSH — sem bashismos, ver design.md D3) que reúne identificação (hostname, timestamp da coleta), distribuição do SO (identificador `ID` do os-release, em minúsculas) e versão, e versão do kernel, e verificar executando-o localmente (ou em um contêiner) sob `sh -n` (checagem de sintaxe) e sob `dash`, e conferindo os campos JSON emitidos (spec: inventory-collection — Dados de Identificação, Dados de Sistema Operacional e Kernel, Coleta por Script em Conexão Única).
- [x] 3.2 Estender o script para enumerar as unidades systemd ativas, marcando cada uma como `service` ou `socket` e com o estado ativo (`active`), e verificar contra um host com pelo menos uma unidade ativa de cada tipo (spec: inventory-collection — Inventário de Serviços).
- [x] 3.3 Estender o script para reportar swap habilitado/desabilitado e tamanho, e verificar contra um host com swap habilitado e um caso com swap desabilitado (spec: inventory-collection — Dados de Swap).
- [x] 3.4 Estender o script para listar as portas em escuta com endereço de vinculação e processo dono, e verificar contra um host com pelo menos um serviço em escuta (spec: inventory-collection — Dados de Portas em Escuta).
- [x] 3.5 Estender o script para enumerar as chaves SSH autorizadas do usuário que conectou com um atributo identificador (comentário/fingerprint), declarando esse escopo no resultado, e verificar contra um host com pelo menos uma chave autorizada presente (spec: inventory-collection — Dados de Chaves SSH Autorizadas).
- [x] 3.6 Estender o script para tentar obter a configuração efetiva de login de root no SSH (por exemplo, via `sshd -T`), marcando o campo como não lido, com um motivo, quando o usuário da coleta não tem privilégio, e verificar os dois ramos — com privilégio (valor devolvido) e sem privilégio (marcado como não lido) — sendo que o ramo sem privilégio é verificado contra o host de laboratório WSL2 (spec: inventory-collection — Configuração Efetiva de Login de Root no SSH).
- [x] 3.7 Estender o script para reportar o mecanismo de sincronização de tempo e o estado ativo, e verificar contra um host com um serviço de sincronização de tempo ativo (spec: inventory-collection — Dados de Sincronização de Tempo).
- [x] 3.8 Garantir que todo campo que o script não consegue ler seja emitido com uma sentinela explícita de não lido (não null, não omitido, não um valor vazio solto) distinta de um valor legitimamente vazio/desabilitado, e verificar com um teste unitário que afirma que o formato da sentinela difere de todo valor "vazio mas lido" usado no restante da saída do script (spec: inventory-collection — Marcação de Campo Não Lido).
- [x] 3.9 Verificar que o script inteiro executa somente comandos de leitura (nenhum de gravação/instalação/habilitação/desabilitação) por uma checklist de revisão estática do código-fonte do script, mais uma execução contra o host de laboratório com comparação do estado antes/depois. O estado comparado é exatamente este, capturado por uma sessão SSH **separada** da do coletor (para a verificação não ser circular): (1) `systemctl list-units --type=service,socket --state=active` (o filtro por tipo exclui o `session-N.scope` que a própria conexão cria); (2) o conteúdo de `/proc/swaps`; (3) a saída de `ss -ltn`; (4) o `authorized_keys` do usuário (hash sha256 do conteúdo e data de modificação). As duas capturas devem ser idênticas. O registro de login da sessão SSH (linha de sessão do `sshd` em log/journal, `last`/wtmp) é **rastro esperado** da própria conexão, não violação: fica fora do conjunto comparado e essa exceção é registrada no resultado da tarefa (spec: inventory-collection — Garantia de Somente Leitura).
- [x] 3.10 Verificar a idempotência: executar a coleta completa duas vezes seguidas contra o host de laboratório, sem mudança de configuração entre elas, e confirmar que todo campo é igual, exceto o timestamp da coleta (spec: inventory-collection — Garantia de Somente Leitura, cenário de coleta repetida idempotente).

## 5. Parser YAML Mínimo de Baseline

- [x] 5.1 Implementar um parser para o subconjunto de YAML necessário ao `baseline.yaml` (mapeamentos em bloco, listas em bloco, escalares, comentários e flow style de uma linha: `[a, b]` e `{chave: valor, outra: [x, y]}`; booleanos somente `true`/`false`), e verificar com testes unitários cobrindo o baseline oficial do enunciado (layout completo, com mapeamentos em linha contendo listas).
- [x] 5.2 Implementar a rejeição explícita de construções não suportadas (âncoras/aliases, streams multi-documento, tags complexas, mapeamento em linha aninhado, flow style multilinha, mapeamento dentro de lista, tipagem implícita ambígua — incluindo `yes`/`no`/`on`/`off` como booleano) com um erro que nomeia a construção e sua localização, e verificar com testes unitários para cada construção rejeitada (spec: baseline-compliance — Parser Mínimo de Baseline).
- [x] 5.3 Ligar as falhas do parser (construção não suportada ou arquivo estruturalmente inválido) ao caminho de falha de execução (código de saída `2`) com uma mensagem que identifica o baseline como o problema, e verificar com um teste unitário usando um arquivo de baseline deliberadamente malformado (spec: baseline-compliance — Baseline Inválido é Falha de Execução).
- [x] 5.4 Implementar a validação do campo `versao` antes de interpretar qualquer regra (conjunto suportado `{1}`), e verificar com testes unitários, no layout oficial, que `versao` ausente, desconhecida (texto, `0`, valor não inteiro) e futura (por exemplo, `2`) saem com código `2`, com mensagens distintas para ausente/desconhecida/futura, sem que nenhuma regra seja avaliada, e que `versao: 1` prossegue (spec: baseline-compliance — Validação da Versão do Baseline; design.md — D5).
- [x] 5.5 Implementar a carga do layout oficial do baseline (`versao`, `aplica_a`, `esperado`, `severidade`): id da regra como caminho pontilhado dentro de `esperado`, ordem de aparição preservada, severidade obtida das listas invertidas, valor `esperado` validado por tipo de regra e regras desconhecidas aceitas; e verificar com testes unitários o baseline oficial do enunciado (todas as regras, ids e severidades), chave de raiz desconhecida (incluindo o antigo `regras`), `aplica_a`/`esperado`/`severidade` ausentes e valor esperado de tipo errado (spec: baseline-compliance — Layout do Baseline).
- [x] 5.6 Implementar as severidades fechadas (`critico`, `alto`, `medio`) e verificar com testes unitários que saem com código `2`, nomeando o problema: chave de severidade fora do conjunto, regra de `esperado` sem severidade, regra em dois níveis e id de severidade inexistente em `esperado`; e que o baseline oficial é aceito (spec: baseline-compliance — Severidades Fechadas).

## 6. Motor de Conformidade

- [x] 6.1 Implementar a avaliação regra a regra (id da regra = caminho pontilhado dentro de `esperado`) produzindo uma entrada por regra do baseline (id da regra, esperado, encontrado, veredito), e verificar com um teste unitário que afirma que a contagem de entradas é igual à contagem de regras para o baseline oficial (spec: baseline-compliance — Uma Entrada de Conformidade por Regra do Baseline).
- [x] 6.2 Implementar a lógica dos três vereditos: `conforme` quando o host atende à regra, `desvio` carregando a severidade declarada pelo baseline quando não atende, e `nao_verificado` carregando um motivo, com `encontrado` igual a `null`, quando o fato subjacente foi marcado como não lido pela coleta, e verificar com testes unitários para os três ramos em cada tipo de regra relevante, incluindo que `severidade` só existe em `desvio` e `motivo` só em `nao_verificado` (spec: baseline-compliance — Modelo de Três Vereditos).
- [x] 6.3 Verificar o determinismo: executar o motor de conformidade duas vezes contra o mesmo inventário e baseline fixos, e confirmar vereditos/severidades idênticos nas duas vezes (spec: baseline-compliance — Comparação Determinística).
- [x] 6.4 Confirmar que o motor de conformidade nunca faz uma segunda consulta ao host nem grava nele — opera somente sobre o objeto de inventário já coletado — verificado por um teste unitário que usa um stub de transporte que faz o teste falhar se for invocado (spec: baseline-compliance — Comparação Local).
- [x] 6.5 Implementar e testar `servicos.ativos` e `servicos.proibidos`: nome sem sufixo é `.service` e `.socket` exige o sufixo explícito; `servicos.ativos` dá `desvio` listando as unidades ausentes ou inativas; `servicos.proibidos` dá `desvio` listando as proibidas presentes; nos dois casos, um caso conforme e um caso com desvio (spec: baseline-compliance — Semântica de Comparação por Tipo de Regra).
- [x] 6.6 Implementar e testar `so.versao_minima` e `kernel.versao_minima` com comparação numérica por componente, com casos que uma comparação textual erraria (`6.10` vs `6.9`, `24.04` vs `22.04`, `5.15.0-101-generic` vs `5.15.0`), o ramo de versão encontrada ilegível (`nao_verificado`) e o ramo de versão mínima ilegível no baseline (baseline inválido, código `2`) (spec: baseline-compliance — Semântica de Comparação por Tipo de Regra).
- [x] 6.7 Implementar e testar `portas_em_escuta.publicas_permitidas` e `portas_em_escuta.somente_rede_interna` com a classificação de endereço interno/público do design.md D7, cobrindo: porta 9100 em `0.0.0.0` é `desvio`; porta 9100 em endereço interno (por exemplo, `172.29.2.241` ou `127.0.0.1`) é `conforme`; porta 9100 em `0.0.0.0` e também em `127.0.0.1` é `desvio`; porta de `somente_rede_interna` inexistente é `desvio`; endereços `*`, `::` e `[::1]` classificados corretamente; porta pública fora da lista de `publicas_permitidas` é `desvio` e porta apenas interna não afeta essa regra (spec: baseline-compliance — Semântica de Comparação por Tipo de Regra).
- [x] 6.8 Implementar e testar `chaves_ssh.emitidas_por`: comentário `platform@metacortex-platform` com emissor `metacortex-platform` é `conforme`; chave sem comentário ou com emissor diferente é `desvio` listando a chave ofensora por identificação/fingerprint sem material completo; conjunto vazio é `conforme`; arquivo não lido é `nao_verificado` (spec: baseline-compliance — Semântica de Comparação por Tipo de Regra).
- [x] 6.9 Implementar e testar as regras booleanas `swap.habilitado`, `ssh.login_de_root` e `ntp.sincronizado`, incluindo o mapeamento do valor efetivo do `sshd` (`no` é `false`; `yes`, `prohibit-password` e `forced-commands-only` são `true`, então `prohibit-password` com esperado `false` é `desvio`) (spec: baseline-compliance — Semântica de Comparação por Tipo de Regra).
- [x] 6.10 Implementar e testar que uma regra do baseline que referencia um fato que a coleta não produz recebe `nao_verificado` com o motivo "a coleta não produz o fato", nunca `conforme` nem `desvio`, contando como uma entrada do relatório, e que o motivo distingue "não produzido pela coleta" de "não lido" (spec: baseline-compliance — Regra sem Fato Coletado é nao_verificado; design.md — D6).
- [x] 6.11 Implementar e testar `so.distribuicao`: distribuição igual à esperada (sem diferenciar maiúsculas de minúsculas) é `conforme`; diferente é `desvio` com a severidade da regra e a distribuição encontrada; fato do SO não lido é `nao_verificado` (spec: baseline-compliance — Semântica de Comparação por Tipo de Regra).
