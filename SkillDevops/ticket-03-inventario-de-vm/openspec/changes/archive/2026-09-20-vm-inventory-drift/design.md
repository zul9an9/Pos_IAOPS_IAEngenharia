# Design

## Context

Projeto greenfield (sem código e sem specs existentes). Roda na máquina de quem opera, nunca como serviço, contra uma VM por invocação. O ambiente de desenvolvimento/validação é Windows com um host de laboratório Ubuntu 26.04 em WSL2, acessível em `orpheu@172.29.2.241:22`. Veja `proposal.md - Why` para o problema que motiva a mudança e `specs/inventory-collection` e `specs/baseline-compliance` para o contrato de comportamento.

Duas restrições moldam todas as decisões abaixo:
- A equipe de infra que mantém a ferramenta é só Python; adicionar uma segunda linguagem (Go) ou uma dependência com SSH embutido (paramiko) tem custo contínuo real para uma CLI pontual e de baixo tráfego.
- A chave privada é uma credencial de cliente/produção que passa por esta ferramenta. Qualquer coisa que aumente a superfície em que a chave é manipulada (parsear, manter em memória, passar por uma biblioteca) aumenta o risco sem benefício de comportamento, já que o cliente `ssh` do sistema já faz isso com segurança.

## Goals / Non-Goals

**Goals:**
- Coleta determinística, em passagem única e só-leitura, da configuração real de um host.
- Um motor de comparação honesto sobre o que não conseguiu verificar (`nao_verificado`), em vez de esconder a falta de privilégio ou de dado.
- Zero dependências novas de runtime além da stdlib do Python 3 e do binário `ssh` do sistema.

**Non-Goals (nível de design, além do escopo da proposta):**
- Sem política de retry/backoff para conexões SSH instáveis — uma única tentativa com `ConnectTimeout` basta na fatia 1; o plantão reexecuta manualmente.
- Sem saída em streaming/parcial enquanto o host é coletado — a ferramenta produz o relatório só depois que a sessão SSH única termina ou falha.
- Sem camada de abstração de "transporte" (backends SSH plugáveis) — existe exatamente um transporte (subprocesso do `ssh` do sistema) e nenhum segundo é previsto.

## Decisions

### D1: Python 3, somente biblioteca padrão
Escolhido porque a equipe que opera a ferramenta é só Python e a fatia 1 não tem perfil de desempenho que justifique uma linguagem compilada.
- **Alternativa — Go**: rejeitada porque adiciona uma segunda linguagem e uma etapa de compilação/release a uma equipe que não constrói nem distribui binários Go, para uma ferramenta cujo gargalo é I/O de rede contra um host, não CPU.
- **Alternativa — Python + paramiko**: rejeitada por dois motivos — (1) adiciona uma dependência de terceiros (e sua dependência transitiva de criptografia) a um caminho sensível de credencial, e (2) faz os bytes da chave privada serem parseados e mantidos pelo nosso próprio processo, em vez de entregues, como caminho, ao binário `ssh` do sistema, bem auditado.

### D2: Cliente `ssh` do sistema via subprocesso, chave passada só como caminho
A ferramenta nunca abre nem lê o arquivo da chave privada. Ela monta o argv do binário `ssh` do sistema — `-i <caminho> -o IdentitiesOnly=yes -o BatchMode=yes -o ConnectTimeout=<n> -o StrictHostKeyChecking=<política> user@host sh -s` (ver D8 sobre `IdentitiesOnly`) — e deixa o cliente `ssh` do SO fazer todo o tratamento de chave e de protocolo no próprio processo. A ferramenta pode fazer `stat` no caminho da chave (para dizer "arquivo não encontrado" com clareza), mas nunca o abre. Nunca é passado `-v`.
- **Alternativa — biblioteca SSH em processo (paramiko ou similar)**: rejeitada — ver D1. Além disso, com uma biblioteca, *nossas* mensagens de exceção em Python poderiam embutir estado relacionado à chave (ex.: um erro de decriptação com bytes da chave) a menos que fossem cuidadosamente higienizadas; a fronteira do subprocesso torna essa classe de vazamento estruturalmente mais difícil, porque a chave nunca entra no nosso espaço de endereçamento.
- **Política de `StrictHostKeyChecking`**: o padrão é `yes`. Em `BatchMode` o `ssh` não pode perguntar nada, então host desconhecido é **recusado** e a execução termina com exit 2 e uma mensagem própria ("chave do host desconhecida ou alterada"). Afrouxar exige flag explícita do operador, `--aceitar-host-novo`, que mapeia para `StrictHostKeyChecking=accept-new` — aceita apenas hosts *novos*; chave de host **alterada** continua sendo recusada mesmo com a flag. A ferramenta nunca usa `StrictHostKeyChecking=no` e nunca usa `UserKnownHostsFile=/dev/null`: o `known_hosts` padrão do operador é sempre respeitado.
- **Consequência para o requisito de confidencialidade**: o que precisa ser garantido é que o **conteúdo** da chave nunca apareça em stdout, stderr, arquivo de saída ou mensagem de erro. Como nosso processo só vê o *caminho* da chave, isso reduz-se a: o stderr do subprocesso é capturado e reescrito em categorias fixas de falha (inalcançável / chave do host / autenticação recusada / outra), nunca repassado cru.
- **O caminho da chave pode aparecer?** Sim, nas mensagens de erro do stderr da própria ferramenta (ex.: "chave privada não encontrada em `<caminho>`"). Motivo: é um dado que o próprio operador digitou, não é segredo, e é o que permite diagnosticar erro de digitação ou de permissão. Não pode aparecer nos relatórios JSON/Markdown (stdout ou arquivo), porque esses circulam fora da máquina do operador e revelariam a estrutura de diretórios dele. O caminho que aparece em mensagens é sempre o que a *ferramenta* formatou; texto de stderr do `ssh` (que pode citar caminhos e outros detalhes) nunca é repassado cru.

### D3: Sessão SSH única, um script `sh` POSIX via stdin, uma resposta JSON
Todos os itens do inventário são coletados por um único script, entregue por stdin a `ssh ... sh -s`, que roda uma vez no host e imprime um objeto JSON em stdout. O interpretador é **`sh`** (POSIX), não `bash`: o script não pode usar bashismos (arrays, `[[ ]]`, `<( )`, `${var,,}` etc.), porque o host alvo pode ter `dash` como `/bin/sh` e não deve ser exigido nada além do POSIX. Cada campo que o script não consegue ler (privilégio, ferramenta ausente etc.) é emitido como sentinela explícita (ex.: `{"read": false, "reason": "..."}`), e não como null solto ou chave omitida, para que o lado local distinga "lido e vazio" de "não lido".
- **Alternativa — uma conexão SSH por fato**: rejeitada — N conexões significam N idas e voltas (lento, e cada uma é uma chance de falha independente) e, como o tempo passa entre elas, fatos como "portas em escuta" e "estado do swap" poderiam descrever o host em instantes diferentes, quebrando o retrato pontual exigido pela spec e a checagem de idempotência (duas execuções seguidas devem concordar, o que é muito mais difícil de garantir se os fatos são reunidos aos poucos, em vários segundos/conexões, sob carga).
- O script em si não decide conformidade — apenas mede e reporta valores crus mais o status lido/não lido. A interpretação fica totalmente fora do host remoto (ver D4).

### D4: A comparação acontece localmente, nunca no host
A única função do script remoto é responder "o que é verdade neste host, agora, até onde um usuário sem privilégio consegue ver". O baseline nunca é enviado ao host nem avaliado nele. Isso mantém o host como mera fonte de fatos e esta ferramenta (informada pelo arquivo de baseline) como única fonte do que é "correto", o que também significa que a invariante de só-leitura nunca pode ser violada por uma evolução da comparação — mudanças na lógica de comparação nunca tocam o script remoto.
- **Alternativa — avaliar contra o baseline remotamente (ex.: subir o baseline e rodar a comparação num script remoto)**: rejeitada — exigiria gravar o baseline no host (viola a só-leitura) ou enviá-lo por pipe para uma segunda passagem remota (viola a decisão de conexão única e cria uma segunda coisa que pode ficar defasada entre execuções).

### D5: Parser YAML mínimo e específico para o `baseline.yaml`, não uma biblioteca geral
O parser suporta só o subconjunto de YAML de que o layout oficial do baseline realmente precisa (mapeamentos em bloco, listas em bloco, escalares, comentários e *flow style de uma linha*: `[a, b]` e `{chave: valor, outra: [x, y]}`, sendo o mapeamento em linha só de escalares ou listas de escalares) e levanta um erro claro de "construção não suportada" para todo o resto (âncoras/aliases, streams multi-documento, tags complexas, mapeamento em linha aninhado, mapeamento dentro de lista, flow multilinha etc.), em vez de coagir ou interpretar mal em silêncio. Booleanos são aceitos **somente** como os literais `true` e `false`; formas ambíguas (`yes`, `no`, `on`, `off`, `y`, `n`) são rejeitadas como construção não suportada, pois é exatamente o tipo de surpresa de tipagem implícita do YAML (`no` → `False`) que transformaria um desvio real em falso `conforme`.
- **Alternativa — PyYAML ou ruamel**: rejeitada principalmente para manter absoluta a fronteira "só stdlib" do D1, mas também porque um parser geral *consegue* parsear construções cuja interpretação esta ferramenta nunca validou (ex.: as surpresas de tipagem implícita acima), que é exatamente o tipo de leitura errada silenciosa que poderia virar um falso `conforme`. Um parser estreito que recusa o que não entende é mais seguro aqui do que um permissivo que entende tudo, mas nem sempre do jeito que o autor do baseline pretendia.
- Esta é a única peça de parsing da ferramenta com risco real de correção (baseline malformado → vereditos errados no parque inteiro), então "recusar construções desconhecidas" é tratado como requisito duro, não como desejável (ver `specs/baseline-compliance` — Parser Mínimo de Baseline).
- **Versão do baseline**: o parser lê o campo `versao` e a ferramenta o valida *antes* de interpretar qualquer regra. O conjunto de versões suportadas hoje é `{1}` (inteiro). Versão ausente, não inteira ou fora do conjunto suportado é falha de execução (exit 2), com mensagem que distingue "ausente", "desconhecida" e "futura" (maior que a suportada, ou seja, baseline escrito para uma ferramenta mais nova). Nunca há interpretação otimista de um baseline de versão que a ferramenta não conhece.

### D6: `nao_verificado` como veredito de primeira classe, não caminho de erro
A fatia 1 sempre coleta com um usuário comum (não root), então algumas regras do baseline (ex.: política efetiva de login de root no SSH, que precisa de `sshd -T` ou de configuração legível só por root) são sabidamente inverificáveis nesse modo. Em vez de fazer a execução inteira falhar, ou de a ferramenta fabricar um "melhor palpite" a partir de um grep em arquivo de configuração (que poderia ler `PermitRootLogin no` num arquivo enquanto o `sshd -T` reporta outra coisa por causa de overrides de `Include` ou de um default herdado), o motor de conformidade trata "não foi possível verificar" como um veredito distinto e sempre honesto, com motivo declarado. Há **duas origens** para esse veredito, ambas com motivo explícito e ambas nunca resultando em `conforme`:
1. o fato foi coletado mas marcado como **não lido** (ex.: falta de privilégio);
2. a regra do baseline referencia um fato que a **coleta simplesmente não produz** (regra que a ferramenta não sabe avaliar, ou fato fora do inventário da fatia 1).
- **Alternativa — falhar a execução inteira quando qualquer regra não puder ser verificada**: rejeitada — uma fonte comum de regras inverificáveis (privilégio limitado) tornaria a ferramenta inutilizável para o seu uso principal (varredura sem privilégio), frustrando o propósito.
- **Alternativa — leitura estática de melhor esforço (ex.: grep em `sshd_config`) reportada como `conforme`/`desvio`**: rejeitada — a leitura estática de um arquivo de configuração não é o mesmo fato que a configuração efetiva do daemon (arquivos `Include` de drop-in, múltiplos blocos `Match` e defaults compilados podem todos mudar o valor efetivo), então reportá-la como se fosse `conforme` seria uma afirmação falsa, o que o design da proposta proíbe explicitamente.

### D7: Layout do baseline, semântica de comparação por tipo de regra e formato das saídas
- **Layout oficial do `baseline.yaml`** (versionado pelo enunciado do ticket; não é livre): `versao`, `aplica_a` (obrigatório, texto não vazio; informativo, sem lógica de casamento nesta fatia), `esperado` (grupos `so`, `kernel`, `servicos`, `swap`, `portas_em_escuta`, `chaves_ssh`, `ssh`, `ntp`, cada um com suas regras) e `severidade` (listas *invertidas*: `critico`, `alto`, `medio`, cada uma listando ids de regras). O **id de uma regra é o caminho pontilhado dentro de `esperado`** (ex.: `so.versao_minima`); a ordem das regras é a de aparição em `esperado`. A severidade de uma regra vem das listas de `severidade`.
- **Severidade é um conjunto fechado** (`critico`, `alto`, `medio`). É baseline inválido (exit 2): chave de severidade fora do conjunto; regra de `esperado` sem severidade declarada; regra em mais de uma lista; id em `severidade` que não existe em `esperado` (um erro de digitação deixaria a regra real sem severidade e a severidade solta sem regra). Regras de `esperado` desconhecidas da ferramenta continuam válidas no baseline e recebem `nao_verificado` (D6), desde que tenham severidade.
- **Comparação por tipo de regra, não por igualdade textual**: cada regra conhecida tem uma semântica própria (distribuição por igualdade sem diferenciar caixa, lista presente/ausente, versão mínima numérica, portas por endereço público/interno, booleano, emissor de chave), definida no contrato em `specs/baseline-compliance`. Versões são comparadas por componente numérico (`6.10` > `6.9`), nunca como texto. "Endereço interno" significa loopback, RFC1918 (10/8, 172.16/12, 192.168/16), link-local e ULA `fc00::/7`; `0.0.0.0`, `::`, `*` e qualquer outro endereço são públicos. `ssh.login_de_root`: ver D9.
- **Formato do JSON (contrato com o Roster)**: `{"host": {endereco, hostname, coletado_em}, "inventario": {so: {distribuicao, versao}, kernel: {versao}, servicos: [{nome, tipo, estado}], swap: {habilitado, tamanho}, portas_em_escuta: [{porta, bind, processo}], chaves_ssh: [{identificacao}], ssh: {login_de_root}, ntp: {sincronizado, mecanismo}}, "conformidade": [{regra, esperado, encontrado, veredito, severidade?, motivo?}], "resumo": {conforme, desvio, nao_verificado, por_severidade: {critico, alto, medio}}}`. Convenções de projeção do inventário coletado:
  - `servicos[].nome` é o nome da unidade **sem** o sufixo, com `tipo` (`service`/`socket`) separado; `estado` é o estado ativo do systemd (`active`).
  - `swap.tamanho` é em **bytes** (inteiro); swap desabilitado é `habilitado: false, tamanho: 0` (lido), diferente de `null`.
  - `chaves_ssh[].identificacao` é o comentário da chave, ou o fingerprint quando não há comentário; o material da chave nunca aparece.
  - `ssh.login_de_root` é booleano (D9); o valor efetivo cru do `sshd` aparece em `encontrado` da regra correspondente.
  - `ntp.mecanismo` é `"nenhum"` quando não há mecanismo ativo (nunca `null`, que significa "não lido").
  - **Campo não lido é `null`** no inventário, nunca `[]`, `0`, `false` nem `""`: fatos em forma de objeto mantêm o objeto com folhas `null` (ex.: `swap: {habilitado: null, tamanho: null}`, para o Roster poder acessar o caminho sem erro); fatos em forma de lista viram `null`. O **motivo** viaja na entrada de `conformidade` (`encontrado: null` + `motivo`).
  - Em `conformidade`, `severidade` aparece só em `desvio` e `motivo` só em `nao_verificado` (com `encontrado: null`); `resumo.por_severidade` conta apenas desvios.
- **Formato do Markdown (para o plantão)**: título `# Inventário — <hostname> (<endereco>)`; linha `Coletado em <data> · baseline v<versao>`; `## Desvios` (tabela Severidade | Regra | Esperado | Encontrado, ordenada crítico > alto > médio, mantendo a ordem do baseline dentro do mesmo nível); `## Não verificado` (tabela Regra | Motivo); `## Conforme` (nomes das regras separados por ` · `). O Markdown mostra primeiro o que exige ação; o inventário completo fica no JSON.
- **Destino das saídas**: o relatório vai para stdout por padrão; `--formato {markdown,json}` escolhe qual (padrão: `markdown`); `--saida-json ARQ` e `--saida-markdown ARQ` gravam em arquivo (as duas juntas geram os dois relatórios numa execução). Mensagens de erro e diagnóstico vão só para stderr, de modo que stdout contém apenas o relatório e pode ser usado em pipe. Falha ao gravar um arquivo de saída é falha de execução (exit 2). Em falha de execução não há relatório (não há inventário).

### D8: `-o IdentitiesOnly=yes` na conexão SSH
Sem `IdentitiesOnly=yes`, o cliente `ssh` também oferece as identidades do agente SSH e as chaves padrão do operador (`~/.ssh/id_*`), então uma autenticação poderia ter sucesso com **outra** chave que não a informada em `-i`. Isso quebra a premissa de que o host é acessado com a chave passada e transformaria o teste de "chave rejeitada" em falso positivo (uma chave errada em `-i` ainda autenticaria por outra identidade). Com `IdentitiesOnly=yes`, só a chave de `-i` é oferecida. Foi uma decisão tomada na implementação e é registrada aqui; o argv montado a inclui e o teste de argv a verifica.

### D9: `PermitRootLogin` com valor `prohibit-password` conta como root habilitado
`sshd -T` devolve `yes`, `no`, `prohibit-password` (antigo `without-password`) ou `forced-commands-only`. Para `ssh.login_de_root` (booleano), só o valor efetivo `no` é `false`; **qualquer outro é `true`**, inclusive `prohibit-password`, que ainda permite login de root por chave. Consequência: com o baseline pedindo `login_de_root: false` e o host reportando `prohibit-password`, o veredito é `desvio`. Tratar `prohibit-password` como `false` esconderia um desvio real (root acessível por chave). Evidência: o coletor rodado como root no WSL do laboratório devolve `prohibit-password`.

## Risks / Trade-offs

- **[Risco] Classificar stderr/códigos de saída do cliente SSH (inalcançável vs. host desconhecido vs. autenticação recusada vs. outro) é intrinsecamente frágil entre versões/locales do OpenSSH.** → Mitigação: classificar primeiro pelo status de saída do `ssh` (bem definido: 255 para falhas de nível de conexão/autenticação) e tratar o texto da mensagem apenas como detalhe suplementar, nunca como único discriminador; a distinção "chave do host" usa o texto como apoio e cai, se não reconhecido, na categoria geral de falha de conexão; o balde de fallback ("outra falha de execução") fica sempre disponível para que um caso não reconhecido ainda saia com exit 2 e uma mensagem decente, em vez de quebrar.
- **[Risco] Um parser YAML escrito à mão sempre suportará uma gramática menor que uma implementação real de YAML, então um `baseline.yaml` legítimo mas ligeiramente incomum pode ser rejeitado como "não suportado".** → Mitigação: documentar o subconjunto suportado (na orientação de autoria do baseline, fora do escopo desta mudança) e falhar de forma ruidosa e específica (nomeando a construção não suportada e sua linha) em vez de com um erro genérico de parse, para que o autor do baseline ajuste o arquivo rapidamente.
- **[Risco] SSH de tentativa única, sem retry, faz uma oscilação transitória de rede aparecer como falha de execução completa (exit 2).** → Mitigação: aceito na fatia 1 conforme o escopo da proposta; o operador reexecuta. O `ConnectTimeout` é mantido curto o bastante para que a nova tentativa manual seja barata.
- **[Risco] Distinguir unidades systemd "service" vs "socket", e calcular a configuração SSH "efetiva", dependem de ferramentas específicas do host (systemd, OpenSSH) presentes e se comportando como esperado.** → Mitigação: fora do escopo suportar hosts sem systemd/OpenSSH na fatia 1 (o parque do baseline e o alvo de laboratório são ambos systemd + OpenSSH); um host sem a ferramenta esperada reporta os campos afetados como não lidos com motivo, em vez de quebrar a coleta inteira.
- **[Risco] Como `nao_verificado` não gera exit 1, um baseline cheio de regras não verificáveis pode sair com exit 0 sem ter verificado quase nada.** → Mitigação: aceito na fatia 1 (o veredito e o motivo aparecem em cada entrada do relatório); o critério de aceite 1 exige, no laboratório, que todas as entradas sejam `conforme` — e não apenas ausência de `desvio` — para provar conformidade real.
- **[Risco] A coleta de chaves SSH autorizadas cobre só o `authorized_keys` do usuário que conectou (sem privilégio não há acesso aos de outros usuários).** → Mitigação: o escopo é declarado na spec e no relatório; a regra `chaves_ssh.emitidas_por` é avaliada apenas sobre esse conjunto.

- **[Risco] O formato do JSON do Roster não tem campo para o motivo de um fato não lido no `inventario`; um fato não lido que nenhuma regra do baseline referencia aparece como `null` sem motivo.** → Mitigação: o formato é contrato externo e não é estendido nesta fatia; o baseline oficial referencia todos os fatos coletados, e o motivo sempre aparece na entrada de `conformidade` da regra correspondente. Se o Roster passar a precisar do motivo, isso é uma mudança de contrato a negociar com ele.

## Migration Plan

Greenfield — não há versão anterior de que migrar ou para a qual voltar. A primeira implantação é: instalar o Python 3 (já presumido presente) e o código-fonte da ferramenta na máquina do operador, sem instalação no servidor e sem migração de dados.
